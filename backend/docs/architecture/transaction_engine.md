# Transaction Engine

## Purpose
Centralize all financial movements. Every monetary event (sale, purchase, salary, expense, reversal) must create a record in the `transactions` collection.

## Transaction States
- `posted` – Normal, active transaction.
- `reversed` – Transaction has been cancelled via a reversal transaction.

(No `pending` or `cancelled` in MVP – corrections are done via reversal only.)

## Reversal Mechanism
- A reversal is a separate transaction with `is_reversal = true` and `reversal_of` pointing to the original transaction.
- **Rules enforced by `finance_hooks`**:
  - Original transaction must exist.
  - Original must not already have a reversal.
  - Cannot reverse a reversal (no chains).
- Reversal amounts are typically opposite sign (e.g., credit becomes debit) – handled by business logic.

## Direction
- `direction`: `in` (money in) or `out` (money out).
- Every transaction must have a valid direction.

## Reference Numbers
- Auto-generated by `reference_number_service` (e.g., `TR-20260608-1234`).
- Reference numbers are human-readable identifiers.
- Database uniqueness is enforced separately through unique indexes.

## Related Collections
- `payments` – record actual cash/bank payment events, linked to transactions via `payment_allocations`.
- `client_ledgers`, `vendor_ledgers`, `financial_account_ledgers` – store balance history.

## Enforcement
- `transactions` is **immutable** (no updates/deletes) – enforced by `immutabilityGuard`.
- Corrections only via reversal transactions.
